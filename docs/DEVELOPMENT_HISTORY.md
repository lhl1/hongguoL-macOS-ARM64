# 从能打开，到好用，再到 Mac 能播放

[← 返回首页](../README.md) · [架构](ARCHITECTURE.md) · [验证证据的范围](VERIFICATION.md)

这份记录总结 2026 年 10 月 7–9 日的开发过程。按“为什么要改、查到了什么、怎样改、怎样检查”来讲，不是原始聊天或调试日志。私人截图、手机号、设备信息和真实响应均未收录。

## 开发路线

| --- | --- | --- |

## 一、先弄懂内容从哪里来

最初的要求不是做静态视频展示，也不是把官网嵌入窗口。需要的是一个独立桌面应用，能请求真实目录、搜索、详情和视频信息，同时按原服务的授权状态播放。

因此先调查 APK 的调用链：界面发起什么请求、数据怎样组织、哪些参数属于分页或筛选、哪些 ID 必须原样保留。发现“视频条目”可能藏在多层结构中，小说和短剧也可能混在同一个大响应里。直接拿到一个数组就渲染，容易把非视频内容当作剧目。

实现分为两层：React 负责自己的界面，Electron 主进程负责接口、媒体和存储。少量原 APK 原生能力通过自行编写的 Java JNI 适配器调用。页面只收到整理后的目录和本机媒体地址，不直接接触账号凭据与播放密钥。

另一个容易被忽略的问题是大整数。服务 ID 可能超过 JavaScript 普通数字能精确表示的范围；一旦被四舍五入，搜索详情、游客身份或账号判断都会失败。因此 ID 使用保真解析和字符串传递，不能“看起来差不多就算同一个”。

这一阶段确立了后续的原则：服务返回错误就显示错误，不用假数据填补；预约和锁集状态保留；真实登录与本地收藏分开报告。

## 二、把播放器变成刷剧体验

能播之后，问题转为交互节奏。最早的切换容易等到网络完成才有动作，让用户感觉点击没有生效；滚轮一次产生多个事件，又可能跳过很多部或很多集。

滚轮因此按一次连续手势处理，而不是“每个事件切一次”。详情/选集抽屉展开时，滚动用于查看内容，不向播放器传递切剧动作。沉浸播放时，滚动改为同剧上一集/下一集；普通发现页保留跨剧刷流和向上回看。

画面处理也经历了多轮调整。用户不希望在拖动进度后看到封面，更不希望下一部加载时又闪出上一部。后来把“正在播放的帧”“用户想去的目标”和“目标是否已解码”分别管理：跳进度时保留原视频帧；切视频时动画立即开始，旧帧不能冒充目标首帧。

一个中间方案是在目标帧未到时停住翻动动画。它虽然减少了错误画面，却像卡住一样。随后改为动画照常完成，目标未就绪就等待，不倒放、不重启动画；第一帧到达后呈现并接着播放。

控制区增加音量、倍速、清晰度和当前/总集数。默认取最高可用清晰度，选项来自服务实际返回。进度条视觉变细，但保持较大的操作区域，避免只好看却很难点击。控制栏自动隐藏，沉浸切集不主动把按钮浮出来。

## 三、让窗口像一个整体

顶部原系统标题栏移除后，需要自己处理最小化、最大化和关闭。曾出现按钮看得见却点不动，原因涉及拖动区域覆盖和事件命中，而不是仅仅缺一个点击函数。后续检查按钮的 no-drag 区域、重叠边界、坐标点击和主进程 IPC。

侧栏和顶部出现过明显分界线，播放器留白也曾是低灰。统一背景、去掉边界、把视频容器全部设为纯黑，才让窗口整体连贯。

播放模式区分常规布局、无边框窗口播放和无边框全屏。切换前保存原状态，退出后恢复。返回和剧名在需要的播放模式中仍可见，不以隐藏所有 UI 为由丢失基本导航。窗口拖动保留，不额外加一条破坏布局的标题栏。

窗口验证不能影响用户使用电脑。因此测试窗口隐藏、音频静音，只在隔离资料中验证坐标与状态。操作系统原生全屏/激活行为不能被隐藏状态模拟替代，报告明确保留这个范围。

## 四、登录问题带来了更清楚的数据边界

短信能收到并不等于登录成功。早期出现“缺少有效会话”、验证码服务错误以及登录后用户信息不兼容。需要确认的是原服务是否真正接受凭据并返回同一账号的有效会话，不能只看一个成功码或自己创建本地用户。

这部分补充了 Cookie、会话回滚、账号匹配、过期状态及云历史条件的测试。相关测试使用受控响应；没有把它们说成真实短信登录或云同步成功。功能仍不完善，所以账号入口放入设置，不占据主要使用流程。

Mac 又遇到钥匙串提示。先前游客保存和启动读取旧账号会触发系统安全存储，拒绝授权可能连目录也受影响。改为 Mac 游客仅存当前进程内存，启动不自动解密旧账号；旧文件和钥匙串条目保留，不明文降级保存。

用户主动实验登录时，保存加密账号仍可能请求 macOS 钥匙串授权。它与管理员提权是不同机制：应用不收集系统密码，也不需要 sudo。Windows 共用分支继续使用 DPAPI。

## 五、Mac“打不开”与“播不了”分开调查

### 先处理启动和准备阶段

用户截图显示准备脚本运行 FFmpeg 自检时被 `Killed: 9`，随后又出现应用“已损坏”提示。这发生在视频服务请求之前，不能直接归因于网络接口。

检查发现原生组件的架构和代码页哈希没有损坏；但旧脚本会无条件覆盖 FFmpeg 供应商签名，也把同一权限配置深度施加到不同种类的嵌套组件，下载隔离属性处理不够明确。即使二进制字节正确，系统仍可能不接受应用的整体信任状态。

`.12` 改为先核对源包，再复制到用户目录的新暂存副本，只在这个副本内处理隔离属性。FFmpeg 保留原签名，框架、Helper 与外层应用按层级处理，需要的部分分别签名。Java、解码器、首帧自检都通过才备份并替换旧安装，失败保留旧版并输出阶段。

这些修复有直接代码证据，但原截图不足以确认 `SIGKILL` 究竟由哪一个系统策略分支触发。因此记录的是“修复已发现的安装缺陷”，而不是声称已经定位唯一的系统杀进程原因。

### 再处理能打开但视频失败

后续日志显示目录、搜索、播放信息可以返回，解码器却很快退出，输出字节为零，界面显示 M102。这把范围缩小到了“解码器打开视频源”阶段。旧错误分类没有足够细节，仍不能断言一定是证书或某个 CDN 状态码。

`.13` 重新分工：由 Electron/Chromium 读取远端 HTTPS，逐次检查来源与重定向，支持 Range/206；FFmpeg 只读受限制的本机随机源地址，再输出本机视频流给页面。原服务允许的加密播放继续遵循原模型与密钥处理，不改锁集授权。

同时增加 source/guest/decoder 的固定诊断分类、HTTP 状态与字节数，不把原始 stderr、真实地址、密钥或安装编号写入日志。取消请求时回收对应源和解码器，不能取消其他新请求。

Windows 主机启用相同 Mac 媒体路径进行隐藏静音回归，验证源桥、真实解码、HTML 首帧、进度与多集。后来用户明确反馈 `.13` 在 Mac 可以正常播放，这成为移植 2.3.4 时采用的工作基线。

## 六、搜索、系列、排行和筛选各有自己的逻辑

搜索不能只请求一次。联想和结果分别处理，分页保留服务给出的上下文；快速输入时，旧请求不应覆盖新词结果。重复请求合并，但返回独立快照，避免修改缓存造成别的页面串数据。

系列剧不能只靠相同标题猜。服务明确关联的作品才合并；不同季分别加载目录和保存进度。用户可以在搜索组、详情和选集看到系列，切季时立即显示目标，旧请求不能把刚选的新季改回去。

排行与探索筛选也不能共用一套想象中的参数。排行保留原服务的分类、演员/系列入口、筛选规则和排序；探索使用对应的分类筛选接口，不能把另一种混合分类页当成官方截图的“筛选”。

正式 2.3.3 对照截图、APK 声明和真实返回，采用行类型到选项 ID 数组的映射。首次、选择变化和翻页是不同请求；单选、多选、必选、数量上限和默认项分别遵循返回规则。字符串 `0` 也可能是有效选项，不能因看起来像 false 就丢掉。

官方日后可能新增行、改标题或调整选项。因此界面读服务配置，而不是永久写死某张截图。换体裁会删除失效选择，分页不能借用另一组条件的游标。预约状态明确显示，不能播放就不把播放按钮伪装成可用。

## 七、正式 2.3.x：把细节统一起来

| 版本 | 用户看到的变化 | 关键实现 |
| --- | --- | --- |
| 2.3.0 | 菜单、箭头、播放器、整体间距更统一 | 菜单互斥展开，视口限位，细进度条与统一 SVG 图标 |
| 2.3.1 | 清晰度/倍速不再弹突兀系统菜单；先简介再播放 | 应用内 SelectMenu，共用详情组件，默认预览与可修改偏好 |
| 2.3.2 | 点击 41 立刻选中 41 | 用户目标集与实际播放集分离，最后请求生效、失败回退 |
| 2.3.3 | 探索筛选依服务动态变化；简介小窗不跳尺寸 | 正确筛选契约，固定几何尺寸，慢网/失败仍稳定 |
| 2.3.4 | 筛选没有横向长条；新增一行一部剧 | 自动换行，共用目录排列，设置保存默认布局 |

这里的“立即反馈”不意味着跳过加载。2.3.2 保留实际播放集作为观看记录来源；目标失败回退，过期成功/失败都不能覆盖新的选择。2.3.3 预览加载前就采用完成后的尺寸，避免内容到达时突然长大。

2.3.4 把排行、探索、筛选、搜索、追剧、记录和演员作品接入同一排列逻辑，切卡片/列表不改排序或分页。页面临时切换不覆盖设置中的默认值，老配置没有新字段时仍用原卡片排列。

## 八、将 2.3.4 移植到可播放的 Mac 基线

本次没有重新猜一套 Mac 解码方案。先比对 `.13` 与 2.3.4，确认六个核心模块完全相同：媒体 broker、Mac 源桥、Mac 传输、游客会话、视频自检与运行路径。主进程新增的是系列、筛选和测试入口，不改已工作的网络/解码初始化。

以 `.13` ZIP 直接为基线，只替换新 app.asar、5 份应用/Helper 版本 plist 和说明，重建校验清单。557 个其他条目保持字节和 Unix 模式，282 个原生资源条目、14 个符号链接保持，FFmpeg 供应商代码页也核对。

本地成品源码 2.3.4、bundle build 2340。组包时曾遇到 Python 3.14 对复用 ZIP 内部偏移元数据的检查，发现后备份失败候选，再通过复制 ZipInfo 并清除旧偏移修正；失败候选不交付。

87 项测试、隐藏合成首帧、启用 Mac 共用路径的真实播放和筛选/排列回归通过。当前主机是 Windows，报告仍明确不代表新版在 Mac 实机执行。新包在 Mac 准备时再次本机自检成功才安装，原 `.13` 和 Windows 工作版未变。

## 九、开源时再整理一次边界

源码开源不等于把开发电脑整个目录上传。复制到独立发布目录，去掉专有资源、捕获响应、账号信息、日志、用户截图与原图标；使用合成测试和原创 SVG。Java 回调保留，研究入口与私人路径移除。

Mac 构建工具改为接受用户自己持有的基线 ZIP，不把私人文件路径硬编码进仓库。文档分别解释源码构建、私有资源、本机安装、系统写入范围和测试边界，避免“克隆成功就应该能播”的误解。

修改前留日期备份、记录范围/版本/SHA256；发布时逐文件核对 Git blob，保留初始仓库历史，不强推覆盖。MIT 只覆盖本项目原创部分，不能替第三方组件授予再分发许可。

## 对后续维护的启发

1. 先定位失败阶段：启动、身份、接口、视频源、解码、画面，分别取证。
2. 把用户操作与网络完成分开，立即反馈，但别提前写入观看记录。
3. 动态业务读服务规则，不把截图写成永久协议。
4. 保留能工作的基线，跨平台移植先对比，不随意替换底层组件。
5. 原生包检查、主机测试、Mac 实机、真实登录是不同证据，分别报告。
